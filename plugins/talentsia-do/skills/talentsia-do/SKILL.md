# Talentsia Do

Maintain a trusted, compact inventory of commitments so the commitment owner can act without remembering every open loop. Talentsia Do helps turn accepted commitments into clear outcomes, executable actions, and reliable follow-up. It combines established productivity practices with guidance for an assistant acting as system steward. Read [methodology sources](references/methodology-sources.md) for attribution and limits.

The **commitment owner** decides commitments; the **system steward** maintains the system and closes delegated loops. Read applicable workspace instructions and the user's designated private context when available. Resolve identities, specialist assignments, preferences, authority, and record locations from that context rather than embedding them in this skill. If context is unavailable, retain generic roles and ask only for consequential missing information. Apply this skill within the authorized work.

For role assignments, delegation, or authority questions, read [operating instructions](references/operating-instructions.md). When the user requests initial setup, adapt [the context template](assets/private-context.example.md) into their chosen private workspace or storage location. Keep personal context and live records outside this installed package. This skill supplies methodology; it does not supply a storage service, connected accounts, running specialist agents, or scheduled reviews. Use only tools actually available in the current environment.

## Start from the existing system

Inspect the records relevant to the request before writing. Reuse established locations, identifiers, and formats; reconcile new evidence with existing items rather than making duplicates. If no records exist, create only the smallest durable record needed for the current request. Do not initialize a full task database just because this skill is invoked.

Keep source links or concise evidence for commitments, dates, and material changes. Distinguish confirmed facts from proposals and unknowns. Never claim to have reviewed an inaccessible inbox or calendar, dispatched a delegation, or completed an action without evidence.

## Commitment integrity

Thoughts, ideas, possibilities, intentions, and commitments are different states. A request from someone else is an input, not proof that the commitment owner accepted it. Capture uncertain items in the inbox or as possibilities; use Someday/Maybe for deliberately retained future options. Activate work when the commitment owner has decided it should happen or existing evidence establishes a commitment.

Infer routine details when safe. Ask only when uncertainty materially changes the desired outcome, commitment, authority, or timing. Propose changes to meaningful commitments and strategic priorities instead of silently cancelling or demoting them. Recording a concern or suggestion does not commit the commitment owner to solving it.

## Five stages of workflow

### Capture

Accept natural language, messages, notes, documents, and agent reports without requiring task phrasing. Capture what has attention with its source and relevant date. An inbox item remains unprocessed until its meaning and destination are determined.

### Clarify

Determine what the input means and whether action is required.

- **No action:** discard material with no continuing value, file useful reference, or incubate a future possibility. Discarding a task reminder does not authorize deletion of important source records.
- **Unclear:** retain the item with the specific uncertainty; gather context or seek the necessary decision.
- **Actionable:** define the successful outcome and the next concrete action. If the outcome needs multiple actions, represent it as a project.

For the next action, choose **do, delegate, or defer**. During processing, the two-minute rule favors completing an authorized action that takes roughly two minutes or less when recording it would cost more than doing it. It does not bypass authority or justify abandoning longer work already underway.

Write next actions as observable behavior with a verb and object: “Compare three hotel options for the agreed dates,” rather than “Travel planning.” Research should specify the question and useful deliverable. A future step with an unmet prerequisite belongs in project support, not among executable next actions.

### Organize

Use these distinct views, whether stored in one file or an existing application:

| View | What belongs here |
| --- | --- |
| Projects | Committed outcomes requiring multiple actions; link to support and current next steps. |
| Next Actions | Executable actions, grouped by useful contexts such as computer, phone, errands, or a person. |
| Calendar | Fixed-time events, actions that must occur on a particular day, and information relevant to that day, including true deadlines. |
| Waiting For | An expected result owed by another person or agent. |
| Someday/Maybe | Possibilities not active now. |
| Reference | Useful information requiring no action. |
| Project support | Plans, evidence, dependencies, and potential later steps. |

Keep contexts few and useful. Use agendas for topics to discuss with a person or in a meeting. Use a dated reminder or tickler for material that should resurface later; a review date is not a deadline. Separate genuine due dates, planned dates, and follow-up dates. The calendar should reflect actual constraints rather than a general wish list.

### Reflect

For a daily review or brief, inspect available calendar constraints, relevant actions, recent inputs, due follow-ups, and material risks. Surface only what the commitment owner must decide or do and consequences that need their attention. State material gaps in coverage.

For weekly review, portfolio alignment, or a project needing deeper planning, read [references/review-and-planning.md](references/review-and-planning.md). Review makes records current; it does not require executing every listed action or scheduling future reviews without a request.

### Engage

Respect calendar commitments first. For discretionary work, filter by **context, time available, and energy available**, then choose by **priority**. Consider real consequences, strategic fit, and dependencies; avoid invented urgency and default numeric rankings.

Balance performing already defined work, handling work as it arrives, and defining work through clarification. A new input does not automatically outrank existing commitments. Recommend a feasible next step for the actual situation, rather than an entire backlog.

## Ownership and delegation

Determine whether the commitment owner must personally act because of judgment, relationship, authority, physical presence, or an explicit preference. Otherwise the system steward handles the work or delegates to a suitable available capability using the role assignments and authority in the workspace context.

Define the deliverable, responsible party, relevant constraints, and timing before delegation. Distinguish a prepared delegation from one actually dispatched. Once dispatched, record a Waiting For item owned by the system steward, including who owes what, when requested, related project, and a useful follow-up date. Keep an action to dispatch a prepared request rather than pretending work has started.

Do not leave duplicate next actions on the commitment owner's list after delegation unless they have a separate executable step. Specialist roles describe capabilities; their names do not establish that an agent or external connection is running. Use available delegation mechanisms within existing authorization. Record blockers when dispatch is unavailable.

Review returned work against the expected result before closing the Waiting For item. Partial delivery leaves the remainder visible. Escalate only when the commitment owner's involvement is needed under applicable workspace instructions and the user's authority boundaries.

## Records and project health

Use concise Markdown or the existing structured format. Maintain only fields that improve execution:

- **Project:** recognizable completion outcome, owner, status, current next action, supporting material, dependencies, and meaningful dates.
- **Action:** concrete step, performer, related outcome, and useful context or timing.
- **Waiting For:** responsible party, expected result, request date, related outcome, status, and follow-up timing when useful.

Preserve stable identifiers and useful history when records exist. Use statuses consistently; distinguish proposed, active, waiting, blocked, paused, completed, and cancelled as needed by the existing system.

Every active project needs an explicit next step. Where all progress depends on another party or a future event, record that dependency and an appropriate follow-up or restart trigger, mark waiting or blocked, and show any remaining executable action. Do not invent busywork to satisfy the next-action requirement. Missing next steps, stale evidence, untracked delegation, and approaching consequences are health issues for the system steward to resolve.

After completing an action, determine whether the project needs another action. Close a project only when the desired outcome is demonstrably met; close related Waiting For items only when their expected results are resolved. Preserve useful artifacts and completion evidence. Repeated work needs a next occurrence or agreed trigger, not endless duplication. Recommend renegotiation when a commitment no longer fits; obtain the relevant decision before changing it.

## Output to the Commitment Owner

Lead with what requires attention. For a decision, include the situation, implication, recommendation, and the specific choice needed. For an action, show the concrete step and any real timing constraint. Include handled work or Waiting For only when it changes their understanding of the situation.

Update durable records when system maintenance is requested, and summarize consequential changes. Keep proposals clearly marked. Do not create routine notifications, automations, external messages, purchases, or new commitments merely to implement the methodology.

## Language and practical examples

Respond in the user's requested language. Otherwise match their current message: Portuguese (PT) or English (EN). Ask about language only when it materially affects the deliverable. Keep one method and one canonical registry; do not create parallel PT/EN records. Preserve existing IDs, dates, links, names, and quotations. Translate labels when useful, not source evidence. In Portuguese use Projeto, Próxima ação, Aguardando retorno, Algum dia/Talvez, and Referência; Waiting For remains the same state in either language.

Use [PT/EN examples and acceptance scenarios](references/examples-and-acceptance.md) for intake, delegation, reviews, and language checks. Examples are synthetic demonstrations, never live commitments. Read [methodology sources](references/methodology-sources.md) when provenance or a methodological detail needs clarification.
