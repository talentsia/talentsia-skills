# Shared Talentsia Do method

Read this reference before applying any skill. Its identical exports let each skill work on hosts that expose only its own folder. This is one bilingual method and one trusted system, not ten separate task lists.

## Language and commitment authority

Respond in the requested language, otherwise match the current Portuguese or English. Preserve IDs, original dates, source quotations and evidence. Translate labels without making parallel PT/EN records.

The human owns commitments and consequential priority changes. The assistant stewards the records and performs authorized work. Ideas, concerns, suggestions and incoming requests are inputs, not proof of acceptance. Keep possibilities and proposed decisions separate from accepted work. Activate an outcome only after acceptance or evidence of an existing commitment.

These skills grant no permission for email, third-party messages, calendar writes, purchases, account creation, access changes, important deletions, delegation dispatch or recurring automation. Prepare drafts/proposals unless the human explicitly authorizes the relevant external action. Use only available tools, respect workspace instructions and verify the actual result before claiming it. Organizing work does not itself authorize messages or events.

## One trusted record

Read relevant user-designated records before writing. Reuse existing locations, formats, statuses and stable IDs. Do not initialize competing lists when another skill is invoked. Personal records and context belong outside the installed plugin; do not inspect unrelated private files.

Match capture against source IDs/links and existing outcomes; update the same item when it is repeated. Preserve useful history. Propose a merge when identity is uncertain. Before writing, compare the current revision/timestamp with the evidence used to plan the change. Reread and reconcile newer updates rather than overwriting them; use conditional writes when available.

If no storage or persistence is available, return a portable Markdown record marked **not saved**, with IDs or proposed IDs, state, evidence and next step. Ask for a destination only when needed to proceed. Never claim to have saved, synchronized, read an inaccessible calendar, sent a request or scheduled a future reminder. A follow-up date written in a record is not a running monitor. With no tools, provide useful drafts or proposed actions and distinguish them from performed work.

## Meaning and destinations

Inbox: unclarified inputs. Projects (Projetos): accepted multi-action outcomes. Next Actions (Próximas ações): executable steps. Calendar: genuine fixed-time/day constraints. Waiting For (Aguardando retorno): a result actually owed by another party, supported by evidence. Reference (Referência): useful non-actionable material. Someday/Maybe (Algum dia/Talvez): retained possibilities, not active commitments. Project support: later steps, materials and dependencies. These are views of one canonical record.

Keep true deadlines, planned work slots, review dates and follow-up dates distinct. Unknown timing stays unknown. Drafting a request leaves an action to dispatch; it is not a dispatched delegation. Only sent-request evidence or an accepted obligation justifies Waiting For. Discarding an inbox reminder does not authorize deleting the source.

Clarify meaning, acceptance, successful outcome and an observable next action with a verb and object. Future steps with unmet prerequisites belong in support. Do, delegate or defer within actual authority. The roughly two-minute heuristic can favor a small authorized action during processing, but cannot expand permissions or interrupt selected work automatically.

Maintain only useful fields: stable ID, source/date, state, outcome/action, responsible party, related project, meaningful timing, evidence and next step or unresolved decision. Mark proposed fields. Active projects need an executable step or explicit dependency/restart trigger, never invented busywork. Completion requires evidence that the desired result was met. Partial delivery leaves the remainder visible. Repeated work needs an agreed next occurrence or trigger, not duplicate records.

## Choose, work and finish

Consider fixed commitments, context, time, energy and importance grounded in the human's priorities and real consequences. Do not invent urgency or mandate numeric scoring. Scale planning to uncertainty; a simple outcome and next action may suffice. Ideas generated while planning remain proposals.

Lead with the useful result and consequential next step/decision. State material coverage gaps, which records changed, and which changes remain proposed. Preserve actual work artifacts and evidence, reconcile results with current records and identify a viable next step. Never promise continuous monitoring or future reviews without a separately configured and verified mechanism.

Read [operating instructions](operating-instructions.md) for authority/delegation questions; [review and planning](review-and-planning.md) for weekly/broader review or deeper project planning; [methodology sources](methodology-sources.md) for attribution. This independent implementation claims no third-party endorsement or guaranteed outcome.

## First use and trusted storage

Do not make setup a prerequisite for a useful conversation. First read applicable workspace instructions and the relevant user-designated record or supplied snapshot. If its location is unknown, ask one focused question only when reading or saving is needed: “Where do you currently keep these commitments?” Never search unrelated personal files. If there is no existing system and durable saving is requested, propose the smallest private record needed, then create it only in an authorized destination. Resolve the record location, owner, timezone when material, available read/write capability and actual permission from the user's context; never embed them in the plugin.

Reuse the existing schema and statuses. For a new minimal Markdown record use ID, type/state, original input and source, accepted outcome if any, executable actions, owner, dependencies, meaningful dates and evidence. Keep Project outcome/owner/status/support and actions distinct; actions retain performer/context/project; Waiting For retains who owes what, request or acceptance evidence/date, related project and follow-up. Proposed identifiers remain proposed until reconciled with the real store. Verify writes by reading the changed record or receiving a tool confirmation. Report precisely what was saved and where. If reading fails, do not write from an assumed old state; use a supplied snapshot or return proposed changes marked not saved. A chat response or Project reference file is not proof of durable task storage.

## Skill handoff and state contract

All workflows use the same record, never an independent registry per skill. Carry across a handoff: record location or supplied snapshot, stable item/project/action IDs, source evidence, current state/revision, accepted outcome, executable actions and dependencies, unresolved decisions, proposed changes and confirmed changes. Do not expose unnecessary personal data. Preserve an input's ID through clarification and link any resulting project/actions to it. Read the receiving SKILL.md and required references before continuing; then reread current records before a write. If that workflow is unavailable, apply only the shared-method steps actually accessible and disclose the limitation, rather than claim another skill ran.

Typical chain: Clear My Head captures inputs → Organize My Work clarifies their disposition → Plan My Day selects existing executable actions → Do With Me produces/records evidence → Review reconciles the same records. A selected action is a view, not a new obligation. A suggested handoff has not been executed. Continue a requested multi-stage chain without asking again at every stage, within existing authority; if only capture was requested, offer clarification rather than silently process the backlog. Reset composes these workflows on the same state.

## Contexts, agendas and bring-forward

Group executable actions by a few useful contexts: available device/tool, place, person or situation. Maintain agenda topics under the relevant person or meeting, linked to their outcome; an agenda is not a Waiting For item unless a result is actually owed. Use existing contexts and agenda lists rather than create duplicates. Several independent actions can be executable for one project at once. Keep all useful available fronts visible; put only steps with unmet prerequisites in support. Never invent work to fill a blocked project.

The calendar contains fixed-time events, actions that truly must occur on a particular day, and information relevant to that day. Keep discretionary aspirations on action lists. Keep deadlines distinct from planned work slots, review dates and follow-up dates.

For material that should resurface later, retain its source/support and agreed date or event trigger in the existing tickler/bring-forward system. Resolve the actual mechanism: a user-maintained dated list checked during review, an existing reminder service, or an explicitly authorized tool configuration. A recorded date does not create a reminder. Check due bring-forward material during the relevant daily/weekly review, clarify it when its trigger is met and record its disposition. If no mechanism exists, provide a proposed dated item marked not saved and explain how the user can review it; do not promise automatic resurfacing or create an automation implicitly.

## Choosing among work

Respect fixed commitments. For discretionary work, first filter by current context, then time available, then energy available; choose among the feasible actions by priority, consequences and stated goals. A high-priority action that cannot be performed in the current context remains visible for another opportunity. Do not force numerical scoring.

Account for three kinds of work: performing predefined actions, handling work as it arrives, and defining work through capture/clarification. Make room to define work when inputs obscure commitments. Assess incoming work against current constraints and consequences; newness alone does not make it more important. Propose tradeoffs or renegotiation when necessary rather than silently displace promises.

## Reference loading and failures

Read the shared core for every workflow. Read review-and-planning for weekly/broader review, for purpose/success/approach uncertainty in a project, or when conflicting priorities call for higher horizons. Read operating-instructions when ownership, delegation or authority needs resolution. Read methodology-sources for provenance. A source link is attribution, not an applied procedure; do not require browsing external sources to perform steps contained in the package.

If a required local reference cannot be read, name the unavailable reference and ask for its relevant section or a supplied copy. Do useful bounded work from instructions actually available, but do not claim the missing method was applied or a full review completed. Do not substitute assumed model knowledge for the missing instructions. With a mobile consolidated reference, use its named section and anchor; if the file is inaccessible, say so before relying on it.
